## 一、背景与三场景使用流程

项目原有的三段式使用流程：

| 场景 | 运行环境 | 说明 |
|------|---------|------|
| ① 首次制作 U盘 | 用户已有的 Windows | `usb-v1.0.ps1` 一键制作（Ventoy + ISO + exFAT 数据分区） |
| ② U盘启动修复 | Live Debian（本项目 ISO） | welcome.sh → claude，**离线维修**系统盘（NTFS 可读写挂载、chntpw 改注册表、数据抢救、引导修复） |
| ③ Windows 内插U盘维修 | 用户已装好的 Windows | **本文档核心**：Windows 侧启动 claude 对在线系统做日常维护 |

场景②与③共用 U盘 exFAT 数据分区 `/config/` 的凭证、系统提示词与任务文本，"U盘 = 身份 + 大脑，电脑 = 一次性运行时"。

## 二、新增功能清单（5 项）

### 功能 1：Windows 侧维修启动器（核心）

- 新建 `repair-on-windows.ps1`（含 bat 双击入口），置于 exFAT 数据分区根目录
- 流程：定位U盘盘符 → 读 `/config/` 凭证 → 注入 `ANTHROPIC_BASE_URL=https://tokeneff.com` 等环境变量 → 检测 `claude` 命令，无则官方安装器在线安装 → 以U盘 `CLAUDE.md` 为系统提示词启动维修会话
- **决策：claude 不内置于U盘**
  - U盘现有二进制是 Linux ELF（~235MB），Windows 不通用
  - 场景③本身需联网走网关，在线安装零额外代价
  - U盘空间留给 ISO 与离线必需品
- 配置覆盖机制【定稿】：脚本设置 `CLAUDE_CONFIG_DIR` 指向本机临时工作副本（启动时从U盘 `/config/claude-config/` 复制到 `%TEMP%\ai-repair\claude\`，因 exFAT 无软链且不可靠）；**不覆写**用户本地 `%USERPROFILE%\.claude\`，收尾仅删除临时副本。避免行为不一致的同时与功能 4"本地零残留"语义自洽
- 启动器需 UAC 提权（维修操作涉及系统级改动与 `%PROGRAMDATA%` 写入）：bat 入口自动请求提权，拒绝提权则仅允许只读诊断类任务

### 功能 2：维修记录系统（按模式分流）

- `/config/settings.conf` 增加 `RECORD_MODE=customer|enterprise`

| 模式 | 适用 | 记录存放 | 拔盘后电脑残留 |
|------|------|---------|:---:|
| customer（上门服务） | 维修人员服务外部用户 | 仅U盘 `/config/records/` | 无（含会话历史清理） |
| enterprise（企业运维） | 维护人员日常维护办公电脑 | 电脑本地 `%PROGRAMDATA%\ai-repair\records\` + U盘留轻量索引 | 保留（可审计、可续修） |

- 收尾时由 claude 自动生成结构化记录（Markdown + YAML 头：机器信息 / 问题 / 处置 / 建议）

### 功能 3：机器指纹与历史召回

- 机器指纹 = 主板序列号（优先 `Get-CimInstance Win32_BaseBoard | Select SerialNumber`；wmic 在 Win11 24H2 起默认移除，仅在 CIM 失败时兜底。比机器名稳，硬盘可能换）
- 插盘时脚本取指纹 → 查U盘索引 → 命中则自动将本机过往维修记录作为上下文喂给 claude

### 功能 4：凭证与残留策略（BYOK 便携身份）

- 一支U盘 = 一个网关身份：场景②③共用 `/config/` 同一份 API key
- key 仅在脚本进程环境变量注入，**不落盘**到用户电脑；拔盘后电脑上的 claude 是"无钥匙空壳"
- 上门模式收尾清理项：会话历史（`~/.claude/projects/` 或临时 CLAUDE_CONFIG_DIR 下的 projects/）、临时配置副本（`%TEMP%\ai-repair\`）
- **决策定稿（2026-10-13）**：enterprise 模式收尾**保留**电脑本地的 `~/.claude/projects/` 会话历史——与"本地留维修记录、可审计可续修"定位一致，续修时 claude 可直接读取上次会话上下文；customer 模式照旧清理。清理动作由收尾任务文本驱动，勿在脚本里硬编码删除
- 已知残余风险：key 在进程环境变量中，维修期间本机进程理论可见（风险低，接受）

### 功能 5：任务文本环境感知增强

- `tasks/*.txt` 需区分在线（③）/离线（②）模式，首行声明当前模式，让 claude 先判断哪些操作必须切离线模式（如锁定的注册表 hive、使用中的系统盘）
- 场景②离线能力清单：chntpw 清密码/改注册表、离线杀毒、数据抢救、引导修复、BitLocker（dislocker，需用户提供恢复密钥）、Windows 快速启动"脏挂载"检测
- 离线写操作建议默认只读挂载、确认后 remount rw（沿用项目破坏性操作防护原则）
- 在线（③）写系统配置（注册表/服务/驱动）前必须先建系统还原点 + 导出将修改的注册表键备份——在线模式的破坏性防护对齐项目决策 5，写入任务文本作为前置步骤

### 功能 6：tokeneff 引流与 key 生命周期管理

**商业背景**：tokeneff 网关即本项目运营方自营，U盘制作技术（制作器）是获客渠道，免费 token 额度是获客预算。U盘由用户/维修人员自行制作（制作器公开下载），**不存在出厂预配 key**——若发放不限流，制作器本身即无限领 key 的入口，这是反薅羊毛要堵的核心口子。

**核心原则**：客户端防护皆可绕过，唯一可靠防线在网关服务端；策略目标不是"杜绝占便宜"，而是把羊毛党消耗控制在获客成本可接受范围内，同时让真实用户顺利走到付费转化。

#### 6.1 发放流程：制作 ≠ 领 key，激活才领

```
下载制作器 → 制作U盘（盘内无 key，仅含激活流程）
→ 用户首次启动（Live 或 Windows 端）
→ 激活请求：U盘序列号 + 机器指纹 + IP（+ 可选推广码）
→ 网关侧判定 → 发放 free-trial 层 key
```

- U盘端零信任：数据分区里的 key 随时可能被提取，故 key 权限天然压低（见 6.2）
- 激活闸门分层（按可承受的注册摩擦选择）：

| 闸门 | 摩擦 | 防护力 | 说明 |
|------|:---:|:---:|------|
| U盘序列号绑定（制作器写入目标盘真实 SN） | 零 | 低-中 | 批量薅需批量真U盘/伪造 SN；真实用户无感 |
| IP/设备指纹限领（同 IP 每天 1-2 个） | 零 | 中 | 少量 NAT 共享网络误伤 |
| 手机号/微信验证码激活 | 中 | 高 | 每号一 key，流失部分嫌麻烦用户 |
| **分层验证【已选定】**：SN + IP 限频零门槛发放；首月用量超 1 亿 token 后再触发一次邮箱验证 | 低 | 高 | 尝鲜零门槛最大化引流；真实深度用户才遇一次摩擦 |

> **决策定稿（2026-10-13）**：采用分层验证。验证阈值为**首月累计 1 亿 token**（讨论中上调，原稿"首周 300 万"仅作网关侧可调初值参考）；验证方式为**邮箱验证码**（V1.1 变更：原定手机号短信改邮箱；V1.2 更正：portal 无现成邮件通道，需新建 SMTP 发信能力，见修订记录），验证通过后**解除后续验证要求（限额不变）**。另设第二阈值：累计 5 亿 token 再验证一次，防重度免费占用。

#### 6.2 服务端限额：封死单 key 套利价值

| 控制项 | 定稿值（宽松组） | 防的套利 |
|------|------|------|
| 周额度 | **2000 万 token** | 天花板 |
| 并发 | **2**（同 key 同时最多 2 请求） | key 挂共享代理/中转站转卖——最关键的措施 |
| RPM/TPM 限速 | 30 请求/分钟 | 批量 API 农场 |
| 模型白名单 | 仅 GLM 入门档 | 高价模型烧额度转卖 |
| 有效期 | 随激活 12 个月，到期转付费/低配档 | 控制"永久免费"的长期敞口 |

> **决策定稿（2026-10-13）**：初版默认值采用**宽松组**（周 2000 万 / 并发 2 / 12 个月），优先体验与转化；所有限额均为网关侧配置项，可按批次 A/B 调整（见 6.6）。对照组（周 1000 万 / 并发 1）作为 B 批参数保留。

#### 6.3 行为风控（检测而非预防）

- 同一 IP/网段出现多个不同 free key → 标记降级（不立即封，避免误伤，先降至 1/10 额度观察）
- 使用模式聚类：真人维修会话为交互式（长间隔、多轮、含工具调用）；API 农场为匀速高频纯文本调用
- U盘序列号与 key 绑定校验失败 → 吊销

#### 6.4 付费转化路径（扩大销售的核心设计）

1. **额度透明**：任务菜单提供"余额查询"任务，免费用户随时可见剩余额度（稀缺感）
2. **用尽软着陆**：降级到低速率/低配模型 + 提示升级 tokeneff 套餐，升级入口（注册/购买 URL）预置在U盘数据分区
3. **场景外钩子**：任务菜单放 1-2 个进阶任务（写代码/分析文档），让用户发现 token 的通用价值
4. **企业运维模式 = B 端入口**：维修人员/运维用量大，免费额度自然不够 → 引导企业套餐
5. **推广码分成【比例已定稿：20%】**：维修人员制作U盘分发他人使用，激活时填其推广码，名下用户付费可分成——把U盘分发者变成销售渠道。分成 = 名下激活用户实际付费金额的 **20%**（网关侧可配），按月结算，提现走 tokeneff 账户余额
6. **归因字段**：key 元数据记录渠道（usb-maker 版本、激活方式、推广码），衡量U盘渠道的激活/留存/付费转化率；免费政策可按批次 A/B 测试（额度、验证时机均为网关配置项，无需改U盘）

#### 6.5 商业结构定性

Razor-and-blades 模式：U盘制作技术是刀架（获客渠道），token 套餐是刀片（持续收入）。反薅羊毛的真实目标是**保护刀片收入的转化率**而非免费额度本身——所有策略以"是否影响真实用户转化"衡量。羊毛党单 key 上限 2000 万 token/周（并发 2 封死转卖）且无法转卖，该消耗计入获客成本。

**防蚕食的主控制是模型白名单（仅 GLM 入门档）**：免费额度再大，企业/重度场景所需的高价模型与能力不在免费层，付费的核心理由始终成立；额度阈值（首月 1 亿、累计 5 亿，见 6.1）只是辅助控制。宽松组免费层的定位是"尝鲜 + 轻度家庭自用"，与付费层（全模型、高并发、企业配额）有明确能力分界。

## 三、明确排除的方案

| 方案 | 排除原因 |
|------|---------|
| 云端直接检测 USB 插拔 | 云服务器看不到用户硬件层；浏览器沙箱禁止读 USB |
| Windows 常驻客户端 | 需分发安装，门槛高，暂不做 |
| U盘内置 Windows 版 claude 二进制 | +250MB 体积，且在线安装方案无额外代价 |

若未来需要云端管理能力，可行路径为"云端管理 + 本地代理"（U盘内 agent 向云端注册/心跳/拉任务），本文档暂不实施。

## 五、技术细节定稿（2026-10-13，原开放问题闭环）

### 5.1 `settings.conf` 格式（welcome.sh 与 repair-on-windows.ps1 共读）

```bash
# /config/settings.conf — bash source 与 PowerShell 逐行解析双兼容
# 规则：KEY=VALUE，等号两侧无空格，值不加引号；# 仅允许整行注释，禁止行内注释（PS 解析须剥离整行注释后逐行 KEY=VALUE 切分）；新增字段只增不改语义
RECORD_MODE=customer
GATEWAY_BASE_URL=https://tokeneff.com
ACTIVATE_URL=https://tokeneff.com/api/usb/activate
BALANCE_URL=https://tokeneff.com/api/usb/balance
PROMO_CODE=
CONFIG_OVERRIDE=1
```

- 字段取值说明（如 RECORD_MODE 的 customer|enterprise）另见于本节文字，不写进 conf，规避行内注释解析歧义
- key 不写本文件：凭证沿用现有 `/config/auth_token`（welcome.sh 已读写的路径，老U盘升级无缝），注入方式沿用 welcome.sh 的 export 模式。exFAT 不支持 Unix 权限位，"0600"仅为挂载参数尽力而为；真实防线在网关侧压低 key 权限（6.2），与零信任原则自洽
- 批次字段 `BATCH_ID=` 由激活响应写入，供网关 A/B 归因（见 5.5）

### 5.2 维修记录模板（Markdown + YAML 头）

```markdown
---
record_id: 20261013-1430-a1b2c3     # 日期-时间-6位随机
date: 2026-10-13 14:30
mode: customer                       # customer | enterprise
machine_fingerprint: PF2ABC123       # 主板序列号（指纹召回的索引键）
machine: "CPU i5-12400 / RAM 16G / 盘 512G NVMe / OS Win11 23H2"
problem: 一句话问题
resolution: 处置摘要
advice: 后续建议
tokens_used: 1234567                 # 会话前后 balance 接口 total_used_monthly 差值；跨月界/网络失败时留空并标注"估算不可用"
duration_min: 35
---
（正文：详细维修过程，由 claude 收尾自动生成）
```

存放：customer → 仅 `/config/records/{fingerprint}/{record_id}.md`；enterprise → `%PROGRAMDATA%\ai-repair\records\{fingerprint}\` + U盘 `/config/records/index/` 轻量索引（仅 record_id/日期/问题一行）。

### 5.3 Windows 侧 claude 安装失败降级链

1. 官方安装器（`irm https://claude.ai/install.ps1 | iex`）失败自动重试 2 次（间隔 10s）
2. 仍失败 → 检测常见原因并给中文指引：安全软件拦截（引导加白名单）/ 代理网络 / 磁盘空间 / PowerShell 执行策略
3. 最终兜底 → 引导场景②："请用此U盘重启电脑进入维修系统，无需在 Windows 内安装任何软件"
- **网关不可达降级**（激活失败 / 会话中网关 5xx、超时，独立于安装失败）：重试 2 次后提示"网关暂不可用"，同样引导场景②离线维修（②不强依赖网关）；会话中途断网则提示保存现场、择时续修
- 红线：不自制/不自托管 claude 分发包（供应链红线沿用），官方渠道唯一

### 5.4 网关激活 API 骨架（tokeneff 侧实现依据）

```
POST /api/usb/activate     {usb_sn, machine_fp, promo_code?, maker_version}
  → 200 {key, tier:"free", batch_id, quota:{weekly_tokens, concurrency, rpm, models[], expires_at}}
  → 429 该 IP 当日激活数超限    → 403 usb_sn 校验失败（伪造 SN 黑名单）
GET  /api/usb/balance      Authorization: key
  → 200 {remaining_weekly, total_used_monthly, expires_at, verification_required}
POST /api/usb/verify       {key, email} → 服务端经 **新建 SMTP 发信通道**（V1.2：portal 原无发信能力）发验证码 → POST /api/usb/verify/confirm {key, code}
  频控（V1.2 定稿）：**按 key、按 email、按 IP 三维度分别** 60s 冷却 + 日限 5 封；验证码有效期 10 分钟，单码尝试上限 5 次，超限作废重发
  （【定稿】终端内交互验证：脚本收集邮箱、用户输入验证码、脚本直接调上述接口——不走网页/URL 跳转，场景②③行为一致）
```

- 服务端要点：SN↔key 绑定表、IP 限频（每 IP 每日 1-2 个）、首月累计用量 ≥1 亿 token 置 `verification_required=true`、行为风控按 6.3
- **同 SN 幂等规则（2026-10-13 补定稿）**：
  - SN 未登记 → 正常发放新 key
  - SN 已登记且 status=active 且未过期 → **幂等返回原 key**（覆盖"数据分区重做/auth_token 丢失"场景；重发 key 的信任级别与首次发放相同，均为持 SN 者——SN 印于 U 盘外壳可拍照获取属残余风险，已由 IP 限频 + SN 黑名单部分缓解，接受）。**两条前提（V1.2 补）**：① usb 激活路径**强制要求 key_encrypted 加密存储**——未配置 Fernet 加密密钥的部署下明文 key 不可恢复，此时降级为吊销旧 key 并经 LiteLLM 重发新 key；② 返回前先查 key 在 LiteLLM 侧的存活状态，已吊销/删除则走重发路径，不返回死 key
  - SN 已登记但 flagged/suspended → 423 拒绝，提示联系支持
  - SN 已登记但 key 过期（12 个月）→ 409，提示走付费/续费通道，不重发 free key
  - 并发竞态：usb_sn 加唯一约束，同 SN 并发激活在事务内只发一次，双方均返回同一 key
  - machine_fp 仅作召回与风控观察字段，不参与幂等判定（同 SN 换主板属正常）
- 归因字段全在 activate 请求与响应中，U盘侧零额外逻辑

### 5.5 welcome.sh（②）与 repair-on-windows.ps1（③）激活改造点

- 共同逻辑（bash / PS 各实现一份，行为一致）：启动时读 `/config/auth_token` → 缺失则调 activate（收集 SN + 指纹，提示可选推广码）→ key 写回 auth_token + BATCH_ID 写入 settings.conf → 每次启动查 balance，`verification_required=true` 时走终端内验证（输邮箱→收码→输码，见 5.4），余额 <10% 时菜单提示
- welcome.sh：插在现有"凭证 export"步骤之前（五步链的第 3 步前置），失败不阻断离线维修（②本身不强依赖 key）；不改动 auth_token 既有读写语义，老U盘（已含 key）升级后直接命中"已有 key"分支，无需迁移
- repair-on-windows.ps1：同逻辑；激活失败或网关不可达**阻断并引导场景②**（③完全依赖网关）

### 5.6 批次 A/B 实验方案

- A 批（基线）= 宽松组（周 2000 万 / 并发 2）；B 批（对照）= 周 1000 万 / 并发 1；其余参数相同
- 分配：按激活序号奇偶分流（随机化单位 = 激活事件；不用 IP 哈希，避免 NAT 网络整批同侧导致系统性偏斜），batch_id 写回 settings.conf
- 观察指标（4 周）：激活率、7 日留存、人均消耗、付费转化率、风控标记率
- 全部为网关配置项热更新，U盘侧零改动；实验结论决定量产默认值
