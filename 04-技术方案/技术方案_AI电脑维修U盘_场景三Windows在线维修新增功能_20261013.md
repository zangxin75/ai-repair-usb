## 一、背景与三场景使用流程

项目原有的三段式使用流程：

| 场景 | 运行环境 | 说明 |
|------|---------|------|
| ① 首次制作 U盘 | 用户已有的 Windows | `usb-v1.0.ps1` 一键制作（Ventoy + ISO + exFAT 数据分区） |
| ② U盘启动修复 | Live Debian（本项目 ISO） | welcome.sh → claude，**离线维修**系统盘（NTFS 可读写挂载、chntpw 改注册表、数据抢救、引导修复） |
| ③ Windows 内插U盘维修 | 用户已装好的 Windows | **本文档核心**：Windows 侧启动 claude 对在线系统做日常维护 |

场景②与③共用 U盘 exFAT 数据分区 `/config/` 的凭证、系统提示词与任务文本，"U盘 = 身份 + 大脑，电脑 = 一次性运行时"。

## 二、新增功能清单（5 项）

### 功能 1：Windows 侧维修启动器（核心）

- 新建 `repair-on-windows.ps1`（含 bat 双击入口），置于 exFAT 数据分区根目录
- 流程：定位U盘盘符 → 读 `/config/` 凭证 → 注入 `ANTHROPIC_BASE_URL=https://tokeneff.com` 等环境变量 → 检测 `claude` 命令，无则官方安装器在线安装 → 以U盘 `CLAUDE.md` 为系统提示词启动维修会话
- **决策：claude 不内置于U盘**
  - U盘现有二进制是 Linux ELF（~235MB），Windows 不通用
  - 场景③本身需联网走网关，在线安装零额外代价
  - U盘空间留给 ISO 与离线必需品
- 配置优先级：U盘的 `CLAUDE.md`/settings 必须覆盖电脑本地 `%USERPROFILE%\.claude\`，避免行为不一致

### 功能 2：维修记录系统（按模式分流）

- `/config/settings.conf` 增加 `RECORD_MODE=customer|enterprise`

| 模式 | 适用 | 记录存放 | 拔盘后电脑残留 |
|------|------|---------|:---:|
| customer（上门服务） | 维修人员服务外部用户 | 仅U盘 `/config/records/` | 无（含会话历史清理） |
| enterprise（企业运维） | 维护人员日常维护办公电脑 | 电脑本地 `%PROGRAMDATA%\ai-repair\records\` + U盘留轻量索引 | 保留（可审计、可续修） |

- 收尾时由 claude 自动生成结构化记录（Markdown + YAML 头：机器信息 / 问题 / 处置 / 建议）

### 功能 3：机器指纹与历史召回

- 机器指纹 = 主板序列号（`wmic baseboard get serialnumber`；比机器名稳，硬盘可能换）
- 插盘时脚本取指纹 → 查U盘索引 → 命中则自动将本机过往维修记录作为上下文喂给 claude

### 功能 4：凭证与残留策略（BYOK 便携身份）

- 一支U盘 = 一个网关身份：场景②③共用 `/config/` 同一份 API key
- key 仅在脚本进程环境变量注入，**不落盘**到用户电脑；拔盘后电脑上的 claude 是"无钥匙空壳"
- 上门模式收尾清理项：会话历史（`~/.claude/projects/`）、被覆盖的本地配置
- 已知残余风险：key 在进程环境变量中，维修期间本机进程理论可见（风险低，接受）

### 功能 5：任务文本环境感知增强

- `tasks/*.txt` 需区分在线（③）/离线（②）模式，首行声明当前模式，让 claude 先判断哪些操作必须切离线模式（如锁定的注册表 hive、使用中的系统盘）
- 场景②离线能力清单：chntpw 清密码/改注册表、离线杀毒、数据抢救、引导修复、BitLocker（dislocker，需用户提供恢复密钥）、Windows 快速启动"脏挂载"检测
- 离线写操作建议默认只读挂载、确认后 remount rw（沿用项目破坏性操作防护原则）

### 功能 6：tokeneff 引流与 key 生命周期管理

**商业背景**：tokeneff 网关即本项目运营方自营，U盘制作技术（制作器）是获客渠道，免费 token 额度是获客预算。U盘由用户/维修人员自行制作（制作器公开下载），**不存在出厂预配 key**——若发放不限流，制作器本身即无限领 key 的入口，这是反薅羊毛要堵的核心口子。

**核心原则**：客户端防护皆可绕过，唯一可靠防线在网关服务端；策略目标不是"杜绝占便宜"，而是把羊毛党消耗控制在获客成本可接受范围内，同时让真实用户顺利走到付费转化。

#### 6.1 发放流程：制作 ≠ 领 key，激活才领

```
下载制作器 → 制作U盘（盘内无 key，仅含激活流程）
→ 用户首次启动（Live 或 Windows 端）
→ 激活请求：U盘序列号 + 机器指纹 + IP（+ 可选推广码）
→ 网关侧判定 → 发放 free-trial 层 key
```

- U盘端零信任：数据分区里的 key 随时可能被提取，故 key 权限天然压低（见 6.2）
- 激活闸门分层（按可承受的注册摩擦选择）：

| 闸门 | 摩擦 | 防护力 | 说明 |
|------|:---:|:---:|------|
| U盘序列号绑定（制作器写入目标盘真实 SN） | 零 | 低-中 | 批量薅需批量真U盘/伪造 SN；真实用户无感 |
| IP/设备指纹限领（同 IP 每天 1-2 个） | 零 | 中 | 少量 NAT 共享网络误伤 |
| 手机号/微信验证码激活 | 中 | 高 | 每号一 key，流失部分嫌麻烦用户 |
| **分层验证（推荐）**：SN + IP 限频；首周用量超阈值（如 300 万 token）后再触发一次身份验证 | 低 | 高 | 尝鲜零门槛最大化引流；深度使用时才验证，真实用户流失率低 |

#### 6.2 服务端限额：封死单 key 套利价值

| 控制项 | 建议值 | 防的套利 |
|------|------|------|
| 周额度 | 1000 万 token | 天花板 |
| 并发 | 1（同 key 同时仅 1 请求） | key 挂共享代理/中转站转卖——最关键的措施 |
| RPM/TPM 限速 | 如 30 请求/分钟 | 批量 API 农场 |
| 模型白名单 | 仅 GLM 入门档 | 高价模型烧额度转卖 |
| 有效期 | 如随激活 12 个月，到期转付费/低配档 | 控制"永久免费"的长期敞口 |

#### 6.3 行为风控（检测而非预防）

- 同一 IP/网段出现多个不同 free key → 标记降级（不立即封，避免误伤，先降至 1/10 额度观察）
- 使用模式聚类：真人维修会话为交互式（长间隔、多轮、含工具调用）；API 农场为匀速高频纯文本调用
- U盘序列号与 key 绑定校验失败 → 吊销

#### 6.4 付费转化路径（扩大销售的核心设计）

1. **额度透明**：任务菜单提供"余额查询"任务，免费用户随时可见剩余额度（稀缺感）
2. **用尽软着陆**：降级到低速率/低配模型 + 提示升级 tokeneff 套餐，升级入口（注册/购买 URL）预置在U盘数据分区
3. **场景外钩子**：任务菜单放 1-2 个进阶任务（写代码/分析文档），让用户发现 token 的通用价值
4. **企业运维模式 = B 端入口**：维修人员/运维用量大，免费额度自然不够 → 引导企业套餐
5. **推广码分成**：维修人员制作U盘分发他人使用，激活时填其推广码，名下用户付费可分成——把U盘分发者变成销售渠道
6. **归因字段**：key 元数据记录渠道（usb-maker 版本、激活方式、推广码），衡量U盘渠道的激活/留存/付费转化率；免费政策可按批次 A/B 测试（额度、验证时机均为网关配置项，无需改U盘）

#### 6.5 商业结构定性

Razor-and-blades 模式：U盘制作技术是刀架（获客渠道），token 套餐是刀片（持续收入）。反薅羊毛的真实目标是**保护刀片收入的转化率**而非免费额度本身——所有策略以"是否影响真实用户转化"衡量。羊毛党单 key 上限 1000 万 token/周且无法转卖，该消耗计入获客成本。

## 三、明确排除的方案

| 方案 | 排除原因 |
|------|---------|
| 云端直接检测 USB 插拔 | 云服务器看不到用户硬件层；浏览器沙箱禁止读 USB |
| Windows 常驻客户端 | 需分发安装，门槛高，暂不做 |
| U盘内置 Windows 版 claude 二进制 | +250MB 体积，且在线安装方案无额外代价 |

若未来需要云端管理能力，可行路径为"云端管理 + 本地代理"（U盘内 agent 向云端注册/心跳/拉任务），本文档暂不实施。

## 四、实施优先级建议

1. **功能 1**（入口脚本）——场景③从 0 到 1 的关键
2. **功能 2 + 3**（记录系统 + 指纹召回）——依赖功能 1 落地
3. **功能 4**（清理逻辑）——随功能 1 一并落地
4. **功能 5**（任务文本修订）——独立可做，随时并行
5. **功能 6**（key 激活与引流）——网关侧与U盘侧并行开发；激活流程依赖功能 1/②的 welcome.sh 改造
