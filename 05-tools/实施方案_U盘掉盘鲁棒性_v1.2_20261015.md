## 1. 问题定义

### 1.1 现象（K1b 实测，2026-10-15）

在真实 Windows 机器上运行制作器，下载完成、Claude/Codex 落盘成功后，**OpenClaw/Pi 解压落盘阶段 U盘从系统消失**，后续所有写入失败，制作器报错中止。同日两次复现。

### 1.2 系统侧证据（Windows 事件日志）

| 时间 | 事件 | 含义 |
|---|---|---|
| 17:33:01 | `disk` ID 51，Harddisk1\DR3 | 盘在读写中报硬件错误 |
| 19:07:18 | `disk` ID 51，Harddisk1\DR1 | 同一块盘重枚举后**再次**报错，时刻精确对应第二次掉盘 |
| 18:07 / 19:19 | Kernel-Power 41 | 用户手动重启，非蓝屏，排除系统侧 |

`disk 51` 由**盘自身**上报：闪存/主控在写入负载下出错，随后从总线消失。两台次掉盘均伴随该事件，因果链完整。

### 1.3 结论与定位

- **直接原因**：该 U盘硬件在持续写入下不稳定（劣质白片闪存的典型表现）。
- **产品问题**：用户用什么盘不可控。制作器当前架构把盘的硬件缺陷放大成**不可恢复的失败**，且以开发者视角的报错暴露给用户。要修的是后者。

## 2. 根因分析：当前架构为何放大烂盘风险

当前落盘路径：下载到本机 TEMP → **tar.exe / Expand-Archive 直接解压到 U盘**（OpenClaw/Pi/Node/PortableGit 均如此），ISO/claude.exe 单文件直拷。

| # | 缺陷 | 后果 |
|---|---|---|
| 1 | 10k+ 小文件逐个直写 USB 闪存（OpenClaw ~10k、**PortableGit 10482 个**） | 小文件随机写是劣质闪存最易出错的负载；总耗时被盘速放大，出错窗口极大 |
| 2 | 无掉盘感知 | 盘消失后按旧路径继续，报天书；脚本 abort |
| 3 | 无文件级续拷 | 掉盘=前功尽弃，全量重跑（又一次 10k 小文件直写，恶性循环） |
| 4 | 无落盘校验 | 静默坏块无从发现 |
| 5 | 报错面向开发者 | 没有「盘掉了→重新插→继续」的用户路径 |

## 3. 解决方案

设计原则：**坏盘不崩、好盘不慢、掉线可续（文件级）、终态可信**。ps1/sh 两侧同构，版本 → 1.3.7（两侧统一）。

### 3.1 A：两段式落盘——本机暂存 + 文件级幂等续拷（核心，覆盖全部写盘段）

```
下载包 → 本机缓存目录                      （sha256 命中即跳过下载，见 §3.2-3）
  → 解压到本机暂存 extract\                （解压在 SSD：快、零闪存损耗、失败重试零成本）
  → robocopy（默认 skip-identical）→ U盘    （外层恢复循环，见 §3.2）
```

- **适用范围（v1.1 扩大）**：OpenClaw / Pi / Node / **PortableGit** 四个解压组件全部走两段式；**ISO 与 claude.exe 单文件拷贝**走 B 的掉盘检测外层循环（单文件无续拷语义，失败整文件重拷即可）。
- **解压与写盘解耦**：解压错误不再打在 U盘上；暂存解压失败=下载包问题，重下载即可。
- **续拷语义（v1.1 修正）**：**文件级幂等**，靠 robocopy 默认「目标文件存在且大小+时间戳一致 → 跳过」实现——OpenClaw 10k 文件掉线重拷最坏只重拷 1 个文件。**不使用 /Z**：其字节级 checkpoint 仅在同一进程内有效，与「进程退出→用户重插→重新调用」的恢复流程不兼容，且有显著性能惩罚。
- **负载整形**：单线程（**替换现有 `/MT:4`，见 ps1:182**）、SSD→USB 整树顺序拷贝对劣质闪存最友好；组件各自独立成段，段间落盘校验。
- sh 侧等价物：`tar -xzf` 到本机暂存 + `rsync -rt --partial --inplace --no-perms --no-owner`（exFAT 不支持 POSIX 属主/权限位，必须禁用，否则每文件报错；**保留 mtime（勿加 --no-times）**——它是重跑时「大小+时间戳一致即跳过」的续拷依据。若真机实测 exFAT mtime 精度（2s 粒度）导致误判重拷，降级为 `--size-only`）。**macOS 自带的是 openrsync**，上述旗标组合需真机验证；不支持则降级为 `cp -R` + §3.3 对账驱动的整目录重拷（对账通过即停，等效幂等）。
- **TEMP 空间预检（v1.1 新增，v1.2 动态口径）**：预检值 = 勾选组件实际包体积（含 Debian ISO ~1.4GB、claude.exe ~236MB）+ 解压树 + 现存缓存之和**动态计算**（全勾峰值 ≈ 4GB），不用定数。两段式开始前检查暂存盘剩余空间，不足则报人话：「本机磁盘空间不足（需要约 X GB），请清理后重试」。
- **残留清理（v1.1 新增）**：成功结束后删除 extract 解压树；**下载缓存保留**于固定目录（见 §3.2-3），带总量上限与过期清理（下次运行时清 30 天前条目）。

### 3.2 B：掉盘感知与用户恢复路径

**判定（v1.1 修正 robocopy 退出码语义）**：robocopy 退出码 **0–7 均为成功**（1=有文件被拷、2=目标有额外文件、3=两者兼有……），**≥8 才是失败**。失败时：

1. **先检测后归因**：`Test-Path <盘符>:\`——盘在 = 普通拷贝错误，重试本段（最多 3 次）；盘不在 = 掉盘，走恢复。
2. **恢复**：盘消失 → 说人话并等待：
   > 「U盘已断开（可能是接口接触不良或U盘不稳定）。请重新插好U盘，插好后按回车继续——已拷贝的文件不会重复拷贝。」
   - 重插后**重新枚举盘符**（盘符可能变化），按 §3.2-4 的 nonce 标记确认是同一目标盘。
   - **`$root` 全流程更新（v1.1 新增）**：重定位成功后更新脚本级 `$root` 变量——后续所有步骤（agents.json、复核、Ventoy 之外的写路径）都引用它，禁止拷贝段私藏副本。sh 侧等价物 `$MNT` 同规则。
   - 续拷 = 重新调 robocopy/rsync，已完整文件自动跳过（文件级幂等）。
3. **终止条件（三振）**：同一组件掉盘/失败累计 ≥3 次 → 停止重试，给出诊断：
   > 「U盘在写入时多次断开，硬件不稳定。已拷贝内容保留在U盘上，换一个U盘后重新运行制作器即可——**下载缓存保留在本机**，换盘重跑无需重新下载。」
   - **缓存目录固定化（v1.1 新增，兑现上述承诺）**：
     - ps1：`$env:TEMP\ai-repair-usb-maker\cache\`（现有路径保留）
     - sh：`~/.cache/ai-repair-usb-maker/`（**弃用 mktemp 工作目录存包**）；`trap` 只清解压临时目录，不动缓存；下载前 sha256 命中缓存即跳过。
4. **防误拷标识（v1.2 修正时机）**：**Ventoy 段完成、数据分区挂载并分配盘符之后**（全新安装经 `/I` 会重建分区清盘，早写会被抹掉；升级安装 `/U` 场景同在该点写入），立即在数据分区根写入标记文件 `.ai-repair-maker-session`（内容：随机 nonce + 数据分区卷标）。nonce 存本机**缓存目录**（`cache\session-nonce`，随下次运行覆盖；不得放解压暂存/trap 管辖目录）。掉盘重定位时：重枚举所有可移动盘 → 逐盘找该标记 → nonce 匹配才认定为原目标盘 → 更新 `$root`。找不到匹配 = 用户插了别的盘，继续等待并提示。**不依赖 agents.json**（其写入时序在组件拷贝之后）。标记文件本身写一半掉盘的兜底：匹配失败时退化为「卷标匹配 + 用户确认」。

### 3.3 C：落盘终态校验（可信完成）

每组件拷贝完成后，对账三项（取代现在的「入口存在性复核」单一检查）：

| 校验 | 方法 | 失败处理 |
|---|---|---|
| 文件数 | 本机暂存树 vs U盘树 递归计数 | 自动补拷一次（幂等续拷），再失败→按掉盘路径处理 |
| 总字节数 | 同上求和 | 同上 |
| 关键入口 | node.exe / openclaw.mjs / pi cli.js / PortableGit bin\git.exe 存在且非 0 字节 | 同上 |

全部通过才写 agents.json 的 `installed:true``——**状态文件只反映可信终态**。
**agents.json 原子写（v1.1 新增，v1.2 明确位置）**：临时文件必须写在**目标同目录**（U盘 `config\` 旁，如 `agents.json.tmp`）→ `Move-Item -Force` 覆盖（同卷 rename 原子）。**禁止**先写 `$env:TEMP` 再移入——那是跨卷 copy+delete，非原子，掉盘瞬间恰好留半截。sh 侧同理 `mv`（同目录）。

### 3.4 D：收尾体验（顺带）

- 拷贝阶段进度统一沿用现有 `Write-Progress` 估算（基于暂存树文件数），**不引入 robocopy /tee 日志解析**（v1.1 取舍：两套进度机制并存徒增复杂度）；拷贝前提示「正在写入U盘，此步最慢，请勿拔盘」。
- 结束阶段（Defender 扫描 10k 句柄尾巴）加一句：「正在等待杀毒软件扫描完成，可能需要几分钟，请勿拔盘」。

## 4. 不解决的问题（明确边界）

- **盘本身坏**：A-D 把「掉盘即全损」降级为「掉盘可续、三振诊断换盘」，但无法让坏盘变好盘。诊断文案给出换盘指引是结论输出，不是责任推卸。
- **USB 口/延长线接触不良**：被掉盘感知吸收，恢复路径相同。
- **Defender 实时扫描拖慢**：只做文案管理（§3.4），不尝试关杀软（越权且危险）。
- **Ventoy 写入段掉盘不在本方案范围**（v1.1 明写）：Ventoy 段现有 Die+重插指引行为保留。

## 6. 验收标准（v1.1 补可测口径）

1. **好盘性能**：好盘全流程总耗时 ≤ 1.3.6 的 110%（计时口径：制作器开始到 agents.json 写完，同机同盘同网络各跑一次取总耗时；网络段波动通过二次跑命中本地缓存消除——缓存命中时对比）。
2. **掉盘恢复（模拟，可执行）**：拷贝阶段手动拔盘→重插→回车，流程续拷至完成且 agents.json 正确（sh 侧须实测**已完整文件被跳过、非整树重拷**，验证 mtime/--size-only 取舍）；盘符变化场景（重插后分配新盘符）同样通过。
3. **三振退出**：同一组件失败**累计** ≥3 次（口径与 §3.2-3 一致）后按其文案退出；换盘重跑时**下载缓存命中、无重新下载**（sh 侧同样验证）。
4. **终态可信**：agents.json 仅在三对账通过后原子写入 `installed:true`。
5. **烂盘真机（尽力项）**：用 K1b 掉盘的同一根盘重跑——扛过去=方案有效；三振退出且文案正确=降级成功。间歇性故障不保证复现，不作为阻断项。
6. 冒烟全绿。
