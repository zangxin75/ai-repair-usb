### 0.2 网关调研结论（决定技术路线）

- 链路：nginx-proxy → 自研 FastAPI api-gateway（proxy/gateway/gateway.py，7067 行）→ litellm-proxy → GLM（bigmodel.cn）
- key 体系现成：portal-backend `POST /api/me/keys` 已实现 LiteLLM virtual key 发放（`_call_litellm/key/generate` + `store_api_key`，落 tenant_api_keys 表）；plans 表已有分层限额（allowed_models/token 配额/RPM）
- 用量现成：api_usage 表 + 聚合管道；支付/充值/邀请返佣（referral_commissions，5%）均有
- **~~邮件通道现成~~（V1.2 更正：为错误结论）**：portal 无任何后端发信代码（站内通知走 notifications 表 + 飞书 webhook），邮箱验证需**新建 SMTP 发信能力**（服务商账号 + SPF/DKIM + 送达率验证），S3 工期 1-2 天
- **技术路线定稿**：所有新逻辑并入 portal-backend（新路由组 /api/usb/*），不动 api-gateway 与 gateway.py；nginx-proxy/nginx.conf 加一条 location

## 2. 分阶段详细任务

### S0 制作器补丁（0.5 天，W 线）

- `usb-v1.0.ps1` / `usb-v1.0.sh`：数据分区初始内容新增——`/config/settings.conf`（按方案 5.1 定稿格式，含空 PROMO_CODE）、`/config/claude-config/`（U盘版 CLAUDE.md/settings 副本）、`maker_version` 文件（激活归因字段）、**升级入口 URL 文件**（方案 6.4：升级页面地址预置落盘，供余额用尽/升级提示跳转）
- 验收：制作的U盘在 Windows/Linux 上可见上述文件；老U盘（无新布局）插入后启动器走兼容分支不报错

### S1 网关数据模型与管理面（1 天，G 线）

- 新迁移 migrate_104+：`usb_activations`（usb_sn **唯一约束**、machine_fp、key_id、batch_id、promo_code、maker_version、activated_at、ip、**status 风控状态机：active/flagged/suspended**）；`usb_verify_events`（key、email、验证时间、**发码限频三维度索引：key/email/IP**）；批次配置表（batch_id → 限额参数，默认 A 宽松组/B 对照组）
- **幂等前提（方案 5.4，V1.2）**：usb 激活路径发放的 key **强制走 key_encrypted 加密存储**；部署未配置 Fernet 加密密钥时，幂等"返回原 key"降级为"吊销旧 key + LiteLLM 重发新 key"——S2 实现按此分支处理
- plans 表新增 free-usb 档：周 2000 万 token、并发 2、RPM 30、模型白名单 GLM 入门档、有效期 365 天
- admin：激活记录查询/吊销、批次参数配置（复用现有 /api/admin/* 模式）
- 验收：`bash run_migrations.sh` 通过；admin 后台可手工发放/吊销一把 free-usb key 并实际调通 /v1/messages

### S2 activate / balance API（2 天，G 线，核心）

- **首半天 spike：租户归属方案**（审计 P0-D 定稿）——activate 是匿名调用，而 store_api_key 必传 tenant_id（database.py:645）。定稿路线：**每次激活建影子租户**（复用 main.py:962 既有 tenant+user+key 同事务模式，影子租户标记 source='usb'），key 挂影子租户；推广分成 20% 归集到推广码绑定的 tokeneff 真实账号（S4 实现），不挂影子租户。spike 产出：影子租户命名/清理策略 + 分成归集路径确认，写入 S1 迁移注释
- portal-backend 新路由组 `/api/usb/*`（独立 app/usb/ 子模块）：
  - `POST /activate`：SN 黑名单校验（伪造 SN 403）→ Redis IP 日限（每 IP 每日 1-2 个，超限 429）→ 影子租户 + key/generate + store_api_key 发 free-usb 档 key → 写 usb_activations → 按激活序号奇偶分 batch_id → 返回 {key, tier, batch_id, quota}
  - `GET /balance`（key 鉴权，直查 tenant_api_keys + api_usage）：{remaining_weekly, total_used_monthly, expires_at, verification_required}
  - **行为风控接口**（方案 6.3）：同 IP/网段 ≥3 个有效 key → 相关激活置 flagged（降级观察，人工复核）；SN↔key 绑定校验失败（同一 SN 换 key 高频请求）→ 吊销处置；使用模式聚类标记留 admin 人工分析，不自动封禁
- nginx-proxy/nginx.conf 加 location 转发（沿用 /api/ 现有规则）
- 执行前确认：portal-backend 单测基建现状（若无需补最小 pytest 骨架）
- 验收：curl 冒烟（正常激活/同 IP 第 3 次 429/伪造 SN 403）；奇偶分流正确写 batch_id；balance 返回与 api_usage 一致；**同 IP 第 3 个 key 激活后前两个被置 flagged**；**SN 绑定校验失败场景 key 被吊销**；**幂等（方案 5.4）：同 SN 重复激活返回原 key；suspended SN 423；过期 SN 409 引导付费；同 SN 并发激活双方拿到同一 key；key 于 LiteLLM 侧已被吊销时幂等分支走重发；未配置加密密钥的部署下幂等分支吊销重发**

### S3 邮箱验证（1-2 天，G 线，可延后）

- **新建 SMTP 发信能力（V1.2 更正：portal 原无发信代码）**：portal-backend 增加发信模块（SMTP 账号走环境变量配置）+ SPF/DKIM 配置 + 送达率冒烟（V1.1"零新依赖"系错误假设，本次复审证实）；`POST /verify`（{key, email}，发码频控 **key/email/IP 三维度各自** 60s 冷却 + 日限 5 封；验证码有效期 10 分钟、单码尝试上限 5 次）+ `/verify/confirm`（通过写 verify_events）
- 阈值触发：balance 计算 total_used_monthly ≥1 亿 或 累计 ≥5 亿 → verification_required=true
- **强制执行不动 gateway.py**：定时任务（每日）对"超阈值且未验证"的 key 调 **LiteLLM `/key/update` 周额度 ×0.1**（按 key 操作，不碰租户级 plan/subscription；幂等：额度已是目标值则跳过）。**竞态规则**：验证通过事件优先——降档任务执行前重查 verification_required，false 则跳过；验证与降档同时发生时以 verify_events 落库时间为准，验证在先即恢复
- 验收：全流程冒烟（发码→验证→恢复）；未验证超阈值 key 次日被降档；验证码频控三维度生效（换 key/换 email/换 IP 各自触发限频）；验证码过期与尝试超限作废；**验证通过后额度恢复原值**

### S4 推广分成与归因（1 天，G 线）

- promo_code → 沿用 referral_commissions 表模式，新增 usb 渠道规则：名下用户付费的 20%（与既有 5% referral 并存，规则独立），分成归集到推广码绑定的 tokeneff 真实账号
- admin 月度结算报表（渠道、激活量、付费转化、分成金额）；归因字段（maker_version/promo_code/batch_id）进激活明细
- **批次配置热更新**（方案 5.6）：admin 修改批次参数后的生效范围明确为——已发 key 由 S3 同款 LiteLLM `/key/update` 批量刷新额度，新激活直接按新参数发；白名单变更仅作用于新发 key（避免误伤存量）
- 验收：模拟付费后分成入账正确；报表可按批次/推广码筛选；批次参数修改后存量 key 额度刷新且新 key 按新参数
